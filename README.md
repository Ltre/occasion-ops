# OccasionOps

> 面向红白事、节日、祭典、演出、庆典及其他临时组织活动的现场事务、资源流转与协同管理系统。

**OccasionOps** 用于管理一场活动中发生的资金、采购、物料、人力、任务、场地、施工、装饰、供应商和现场交接等事务。

它不是单纯的记账软件、库存软件或任务管理软件。项目希望通过统一的**活动流水**，还原一件事情从提出、执行、交接到结算的完整过程，让负责人随时知道：钱在哪里、物在哪里、事情由谁负责，以及还有哪些事项没有闭环。

> A field operations and resource-flow management system for ceremonies, festivals, performances, community events, weddings, funerals, and other temporary organized activities.

## 为什么开发 OccasionOps

红白事、节日祭典、演出庆典、宗族及社区活动通常具有以下特点：

- 筹备时间短，现场变化频繁；
- 参与人员多，职责经常临时指定或调整；
- 收款、付款、采购和物料可能经过多人之手；
- 活动资金可能分散在多个账户、现金箱和保管人手中；
- 采购人、付款人、收货人和验收人不一定是同一个人；
- 大量决定通过口头、电话、群聊或语音临时作出；
- 现场人员一直在走动，无法完成复杂的手机操作；
- 活动结束后，需要重新整理礼金、费用、垫付款、库存、押金和交接事项。

传统工具通常只能解决其中一部分问题：

- 记账软件能记录收入和支出，但很难表达代收、转交、换现、垫付和多人经手；
- 库存软件能记录数量，但很难说明物料为何产生、由谁领取、用于哪项任务；
- 任务软件能安排工作，但通常不关联采购、资金、物料和现场证据；
- 通用活动系统多用于报名、票务和日程，不适合复杂的现场事务流转。

OccasionOps 希望把这些分散信息整理为可记录、可关联、可核对、可追溯的活动流水。

## 适用场景

OccasionOps 不限定于某一种活动类型，可用于：

- 婚礼、寿宴、满月宴等红事；
- 丧礼、追悼、祭扫等白事；
- 节日、庙会、祭典及民俗活动；
- 演出、晚会、庆典和展演活动；
- 宗族、社区、村镇和公益活动；
- 临时宴席、大型聚会及接待活动；
- 其他需要多人协作、资源调度和现场执行的临时活动。

## 项目希望回答的问题

活动负责人应当能够随时回答：

1. 钱从哪里来？
2. 钱现在位于哪个账户、现金箱或保管人手中？
3. 哪些资金只是内部转移，哪些才是真实收入或支出？
4. 谁垫付了费用，是否已经报销？
5. 哪些商家还有尾款、押金或退款没有结清？
6. 物料买了多少、收到多少、用了多少，现在在哪里？
7. 哪些物品是借用或租赁的，活动后需要归还？
8. 每件事情由谁负责，是否发生过转交？
9. 哪些任务、款项、物料和交接仍未完成？
10. 某项决定由谁在什么时候作出，依据是什么？
11. 活动结束后，能否快速生成完整、可核对的汇总？

## 核心概念：统一活动流水

OccasionOps 不把资金、采购、物料和任务视为互相孤立的模块。

活动中发生的每个重要事实，都可以形成一条流水，例如：

- 收到一笔礼金；
- 将一笔款项转交给其他人；
- 领取一笔备用金；
- 使用个人资金垫付采购费用；
- 采购物料到货并由他人验收；
- 将物料分发到厨房、舞台或接待区；
- 将任务临时转交给另一名人员；
- 商家完成施工，等待验收和结算；
- 租赁物品归还，押金退回到另一个账户。

这些流水可以彼此关联，从而还原完整过程：

```text
采购需求
  → 审批或确认
  → 询价与下单
  → 领取备用金或个人垫付
  → 对外付款
  → 到货与验收
  → 入库、分发或直接使用
  → 退货、余料或损耗处理
  → 交回余款或申请报销
  → 商家尾款、退款或押金结清
```

每条流水至少需要描述：

- 何时发生；
- 由谁记录；
- 由谁实际执行；
- 涉及什么人、资金、物料、任务、场地或商家；
- 从哪里来、到哪里去；
- 金额或数量；
- 当前状态；
- 相关证据；
- 与其他流水的关联关系。

现场人员不需要填写全部字段。系统应根据当前活动、人员身份、操作入口和上下文自动补充结构化信息。

## 关键业务原则

### 1. 礼金归属与实际资金到账分离

一份礼金可能由多人共同表达，也可能由其中一人统一付款；一笔转账也可能经过收礼人员、家属和理事会成员多次转交。

系统需要分别记录：

- 礼金归属人或归属家庭；
- 实际付款人；
- 代收人和转交人；
- 支付方式；
- 实际到账账户或现金保管人；
- 一笔款项对应的多个礼金主体；
- 尚未确认归属的款项。

礼金账和资金账需要相互关联，但不能被强行合并为同一种记录。

### 2. 内部资金流转不等于活动收支

活动内部的转账、提现、换现、现金交接和资金归集，只改变资金所在位置，不应重复计算为活动收入或支出。

系统需要明确区分：

- 外部收入；
- 对外支出；
- 内部账户转账；
- 提现或换现；
- 现金交接；
- 备用金领取；
- 个人垫付；
- 报销；
- 余款退回；
- 订金、押金、退款和尾款。

例如：

```text
主账户转出 5,000 元给理事 A
  → 理事 A 换成 5,000 元现金
  → 理事 A 将现金交给理事 B
  → 理事 B 支付商家 800 元
```

前三步属于资金位置变化，只有最后支付给商家的 800 元属于真实活动支出。

### 3. 一次采购由多条关联流水组成

一次采购可能由不同人员分别完成：

- 需求提出人；
- 批准或确认人；
- 询价人；
- 实际采购人；
- 垫付款人或公款付款人；
- 收货人；
- 验收人；
- 入库或保管人；
- 报销和结算负责人。

系统不应把采购简化为“某人买了某物”一条记录，而应允许各环节独立记录并自动关联。

### 4. 资金和物料始终具有当前位置

系统不仅要知道发生过什么，还要知道资源当前在哪里。

资金位置可能包括：

- 家属或负责人的银行卡、微信或支付宝；
- 理事会资金池；
- 现场现金箱；
- 临时保管人；
- 采购人的个人账户；
- 商家占用的订金或押金；
- 尚未转交的代收资金。

物料位置可能包括：

- 临时仓库；
- 厨房；
- 舞台；
- 接待区；
- 施工区域；
- 某位人员手中；
- 商家或租赁方处；
- 已借出、已归还或待处理状态。

### 5. 重要记录应可追溯

涉及资金、礼金、库存、责任和结算的记录，不应被无痕覆盖或删除。

修改应通过补充、更正、作废或关联新流水完成，并保留：

- 原始记录；
- 修改前后的内容；
- 操作人；
- 操作时间；
- 修改原因；
- 原始图片、票据、截图或语音。

- 退回余款；
- 订金、尾款、押金和退款；
- 余额盘点和差异登记。

- 到货、收货和验收；

- 材料和工具到场；

- 收据、发票和采购小票；
- 礼簿照片；
- 报价单和聊天截图；
- 到货、施工和验收照片；
- 语音说明和联系方式。

## 核心管理视图

系统可以根据统一流水自动整理出不同视图，而不是要求用户重复记多套账。

### 礼金与收款视图

用于查看：

- 谁表达了礼金；
- 谁实际付款；
- 谁代收或转交；
- 款项实际进入哪里；
- 哪些合并款项尚未拆分；
- 哪些收款尚未确认归属。

### 资金位置视图

用于查看：

- 活动可用资金总额；
- 资金分别位于哪些账户、现金箱和人员手中；
- 哪些属于押金、订金或暂不可用资金；
- 理论余额与实际盘点差异。

### 收支、垫付与结算视图

用于查看：

- 真实收入和对外支出；
- 支出类别和用途；
- 谁仍有垫付款未报销；
- 谁领取了备用金但尚未交账；
- 哪些商家仍有尾款、退款或押金未结清；
- 是否存在可能的重复报销或重复记账。

### 物料与资产视图

用于查看：

- 采购、到货、领用和剩余数量；
- 物料当前位置和保管人；
- 借用或租赁物品的归还状态；
- 损坏、遗失和待处置物料。

### 任务与责任视图

用于查看：

- 当前任务和负责人；
- 已完成、超时和异常事项；
- 无人负责的任务；
- 任务转交和班次交接历史；
- 依赖采购、物料、车辆或商家的待办事项。

## 现场使用原则

### 1. 记录动作应足够简单

现场人员通常只应完成以下一种或几种动作：

- 点一个按钮；
- 说一句话；
- 拍一张照片；
- 输入一个金额或数量；
- 选择一个人员、账户或位置；
- 点击确认。

系统再根据上下文补充结构化字段。

### 2. 使用生活化语言

前台不要求用户理解会计、仓储或项目管理术语。

常用入口可以是：

- 收到一笔；
- 花了一笔；
- 转交一笔；
- 我先垫付；
- 领一笔备用金；
- 东西到了；
- 有人领走了；
- 这件事交给他；
- 商家还没来；
- 先拍下来；
- 先说一句，稍后整理。

### 3. 允许不完整记录

现场人员可以先记录金额、照片、语音或一句简单说明，系统将其标记为“待整理”或“待确认”。

信息不完整不应阻止记录，因为“先留下事实”比“要求当场填完整表单”更重要。

### 4. 支持临时外部人员参与

采购人、司机、帮工或商家可能不属于固定活动成员。

系统应支持通过二维码、一次性链接或临时身份完成指定操作，无需进入完整后台。临时人员只能查看和提交被授权的事项，活动结束后权限可自动失效。

### 5. 适配复杂现场环境

系统需要考虑：

- 老年用户和不熟悉智能手机的用户；
- 方言与普通话混合语音；
- 单手操作和大按钮；
- 户外强光和嘈杂环境；
- 网络不稳定或短暂离线；
- 多人共用设备；
- 不愿安装应用的临时人员；
- 隐私敏感数据的最小权限访问。

## AI 辅助能力

AI 的价值不只是识别票据文字，而是帮助还原、关联和检查活动流水。

计划逐步支持：

- 将语音描述转换为结构化流水；
- 从票据、截图和照片中提取金额、时间、商家和商品；
- 自动拆解一句话中的多条关联操作；
- 识别一笔款项是收入、支出还是内部转移；
- 匹配个人垫付与后续报销；
- 匹配订金、尾款、退款和押金；
- 识别重复截图、重复付款或重复录入；
- 自动关联采购、付款、到货、入库和领用记录；
- 发现未报销、未交账、未付款、未退款和未归还事项；
- 检查资金、物料和任务是否形成闭环；
- 生成每日简报、异常清单和活动总结；
- 支持自然语言查询活动状态。

例如：

> “我从理事那里领了 3,000 元现金，买菜用了 1,860 元，运费 120 元，剩下 1,020 元交给二叔了。”

AI 可以建议拆分为：

1. 领取备用金 3,000 元；
2. 菜品支出 1,860 元；
3. 运费支出 120 元；
4. 剩余现金 1,020 元转交给二叔；
5. 检查金额是否闭合。

AI 只负责辅助整理、匹配和发现问题。重要资金、礼金、物料和责任记录仍需由相关人员确认。

## 主要角色与权限

系统初步考虑支持：

- 活动总负责人；
- 家属或主办方负责人；
- 理事会成员；
- 管账人员；
- 收礼人员；
- 采购人员；
- 物料管理员；
- 场地、施工和装饰负责人；
- 任务负责人和临时帮工；
- 司机和运输人员；
- 外部供应商；
- 审核和只读查看人员。

权限不仅需要限制功能，还需要限制数据范围。

例如：

- 临时采购人员可以提交自己的采购和垫付记录，但不能查看全部礼金；
- 收礼人员可以登记收款，但不一定能查看活动总资产；
- 商家只能查看与自己相关的订单、到场、验收和结算事项；
- 审核人员可以查看流水和修改历史，但不能执行付款或删除记录。

## 初版范围（MVP）

第一阶段优先验证四个核心闭环。

### 1. 资金闭环

- 活动收入；
- 多账户、现金箱和资金保管人；
- 内部转账、提现、换现和现金交接；
- 资金归集；
- 理论余额与盘点。

### 2. 支出闭环

- 活动支出；
- 个人垫付；
- 备用金；
- 报销；
- 余款退回；
- 商家订金、尾款、退款和押金。

### 3. 采购与物料闭环

- 采购需求；
- 下单和付款；
- 到货和验收；
- 入库、领用和调拨；
- 退货、剩余和归还；
- 物料当前位置和保管人。

### 4. 任务与交接闭环

- 创建和指派任务；
- 执行反馈；
- 临时换人和转交；
- 完成确认；
- 异常和超时；
- 班次和现场交接。

## 暂不作为初版重点

为避免项目在早期失去焦点，以下能力暂不作为第一阶段核心目标：

- 通用票务和在线报名；
- 大型商业 ERP 的完整财务功能；
- 正式会计凭证和税务申报；
- 复杂的人力资源和薪资系统；
- 专业工程项目管理；
- 面向单一婚礼或殡葬流程的固定模板。

后续可以在统一流水和权限模型稳定后逐步扩展。

## 项目状态

OccasionOps 当前处于需求梳理、领域建模和产品设计阶段。

现阶段重点包括：

- 收集真实活动中的复杂流转案例；
- 设计统一活动流水模型；
- 设计资金位置、物料位置和责任交接关系；
- 设计适合现场使用的低门槛交互；
- 确定第一阶段最小可用版本；
- 设计 AI 自动整理与人工确认机制。

项目尚未进入稳定版本，不建议直接用于真实活动中的正式财务管理或关键责任认定。
