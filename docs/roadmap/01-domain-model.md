# 统一流水与领域模型

## 1. 目标

统一流水是 OccasionOps 的核心。资金、采购、物料、人员、任务、场地和施工不应各自形成互不相干的数据孤岛，而应通过统一的事实记录和关联关系还原完整活动过程。

## 2. 核心领域对象

### Activity（活动）

活动是数据隔离和权限控制的基本边界。

建议字段：

- 名称、类型、状态；
- 开始时间、结束时间；
- 地点和时区；
- 主办方或主要负责人；
- 当前阶段：筹备、搭建、进行、收尾、结算、归档；
- 数据保留与归档策略。

### Participant（参与者）

参与者可以是注册用户，也可以是临时人员、商家联系人或仅被记录的相关人。

需要区分：

- 系统账号；
- 活动成员身份；
- 现实中的人员或组织实体；
- 联系方式；
- 是否允许登录；
- 是否为临时身份。

### RoleAssignment（角色授予）

角色是某人在某个活动中的职责和权限，不应直接固化在全局用户对象上。

例如同一个人在活动 A 是管账人，在活动 B 可能只是采购协助者。

### FlowRecord（活动流水）

所有重要事实的统一记录载体。

建议最小字段：

- `id`：全局唯一标识；
- `activity_id`：所属活动；
- `type`：流水类型；
- `occurred_at`：实际发生时间；
- `recorded_at`：录入时间；
- `recorded_by`：记录人；
- `performed_by`：实际操作人；
- `source_ref`：来源对象；
- `target_ref`：去向对象；
- `amount` / `quantity`：金额或数量；
- `unit` / `currency`：单位或币种；
- `status`：草稿、待整理、待确认、已确认、已结算、争议、作废；
- `summary`：人可读摘要；
- `metadata`：类型特有结构化字段；
- `created_from`：手工、语音、图片、导入、AI 建议；
- `confidence`：AI 识别可信度；
- `version`：并发控制版本。

### ResourceLocation（资源位置）

表示资金或物料当前所在位置。

位置类型可包括：

- 银行卡、微信、支付宝；
- 现金箱；
- 人员保管；
- 仓库、厨房、舞台、接待区；
- 车辆；
- 商家占用；
- 在途；
- 未知或待确认。

### Attachment（附件与证据）

附件必须与原始流水分离保存，并允许一份附件关联多条流水。

类型包括：

- 票据；
- 付款截图；
- 礼簿照片；
- 报价单；
- 语音；
- 到货、施工和验收照片；
- 聊天截图；
- 合同或文档。

### Link（流水关联）

流水之间需要显式关系，而不是只靠备注文字。

建议关系类型：

- `caused_by`：由某需求或决定引起；
- `fulfills`：完成某需求或任务；
- `transfers_from` / `transfers_to`：内部转移；
- `reimburses`：报销某垫付；
- `settles`：结算某订单、尾款或押金；
- `receives`：对应某采购或交付；
- `consumes`：某任务消耗某物料；
- `corrects`：更正原记录；
- `voids`：作废原记录；
- `duplicates`：疑似重复；
- `splits_into` / `merged_from`：拆分与合并；
- `hands_over`：责任或资源交接。

## 3. 流水分类

统一模型不等于所有类型都塞进同一套字段。建议采用“公共字段 + 类型载荷”的方式。

一级分类：

- 资金；
- 礼金与归属；
- 采购；
- 物料；
- 人员与任务；
- 场地与施工；
- 运输与车辆；
- 决策与异常；
- 证据与说明。

每个一级分类再维护稳定的动作词典，例如：收取、转交、支付、领用、调拨、归还、分派、验收、作废。

## 4. 关键不变量

系统必须维护以下业务不变量：

1. 已确认的重要流水不能直接物理删除。
2. 内部资金转移不能改变活动净收入或净支出。
3. 物料调拨不能改变活动总库存，只改变位置库存。
4. 报销不能重复结算同一垫付款余额。
5. 一笔备用金的支出、转交和退回之和不能无解释地超过领取金额。
6. 一条更正记录必须引用被更正记录。
7. 每条流水必须保留记录人、记录时间和来源。
8. AI 建议不得直接改变已确认事实。
9. 同一外部交易标识在同一活动中应具备幂等保护。
10. 所有跨位置转移必须同时记录来源和去向。

## 5. 状态模型

建议通用状态：

- `draft`：本地或未提交草稿；
- `pending_enrichment`：信息不足，待整理；
- `pending_confirmation`：AI 或他人录入，待确认；
- `confirmed`：事实已确认；
- `partially_settled`：部分闭环；
- `settled`：已完成结算或交接；
- `disputed`：有争议；
- `voided`：已作废；
- `superseded`：已被更正记录替代。

不同业务对象可拥有专门状态，但必须映射到通用状态，方便统一待办和统计。

## 6. 聚合视图

业务页面不直接让用户面对抽象流水，而是通过投影生成：

- 礼金视图；
- 资金位置账；
- 收支账；
- 垫付与报销账；
- 商家结算账；
- 物料库存与位置账；
- 任务和责任看板；
- 场地施工进度；
- 异常与待确认工作台。

这些视图应可从流水重建，避免把聚合结果当作唯一事实来源。

## 7. 数据模型开发计划

### P0：术语与原型

- 编制流水类型和关系类型词典；
- 用 20 个真实复杂场景验证模型；
- 输出实体关系图；
- 明确哪些字段强类型化，哪些保留扩展载荷；
- 确定 ID、时间、金额和数量精度规则。

### P1：基础存储

- 实现活动、参与者、角色、流水、位置、附件和关联表；
- 实现追加、更正、作废和历史记录；
- 实现幂等键和并发版本；
- 实现基础查询和分页。

### P2：投影与闭环

- 建立资金、库存、任务等投影；
- 实现未闭环事项查询；
- 实现流水关联建议和人工确认；
- 实现投影重建与一致性检查。

## 8. 验收标准

- 能用统一模型表示至少 20 个典型与异常场景；
- 一笔采购可关联需求、付款、到货、领用、报销和结算；
- 一笔资金可追踪每次位置变化而不重复计算收支；
- 一批物料可追踪当前位置和保管人；
- 修改历史可以完整还原；
- 业务视图能够从流水重新计算；
- 新增流水类型时无需破坏已有公共结构。
