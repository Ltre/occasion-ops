## 变更摘要

项目文档必须可以合并到 `main` 并继续随任何新分支复用。除非项目所有者在当次任务中明确要求固定分支，通用文档不得写死某个开发分支。

执行文件修改时，若当次提示明确指定分支，则使用指定分支；否则使用 Codex 或当前执行环境已经配置、检出或选定的工作分支。

## 原来的需求

- Work/Codex 交接文档把某个临时开发分支写成“当前规划分支”；
- 推荐提示中直接指定固定分支；
- 部分开发进度与测试记录将临时分支写成长期规则或固定测试目标；
- 没有明确说明用户未指定分支时应遵循执行环境的工作分支。

## 改动后的需求

### 文档可移植性

- `docs/` 中的通用说明、roadmap、模板和 Agent 指引不得绑定某个临时分支；
- 文档应使用“当前工作分支”“执行环境指定分支”“目标分支”等通用表述；
- 只有当分支名本身是需求、迁移或历史证据不可缺少的一部分时，才可记录具体分支，并应说明其为特定上下文而非默认规则。

### 分支选择优先级

1. 项目所有者在当次提示中明确指定的分支；
2. Codex 环境中已配置、检出或选定的工作分支；
3. 其他 Agent 或集成的当前工作分支／目标分支。

除非项目所有者明确要求，不得：

- 因文档中出现过某个分支名就切换到该分支；
- 默认改到 `main`；
- 擅自创建新分支；
- 把一次任务的临时分支写成项目永久规则。

### 开发与测试记录

- `dev-*` 和 `test-*` 可以记录“当次执行环境的工作分支”，但模板和可复用规则不得预设具体分支名；
- 分支追溯优先通过关联 PR、commit 和 Issue 完成；
- 历史记录中若固定分支表述会误导后续 Agent，应改成上下文说明或通用表述。

## 变更原因

- `docs/` 将合并到 `main` 并随未来分支复用；
- 写死临时分支会导致 Agent 在错误分支操作；
- Codex 环境已经负责指定工作分支，文档不应覆盖运行时选择；
- 分支策略应由用户当次指令和执行环境决定，而不是由历史文档决定。

## 影响分析

### 产品与业务

不改变产品功能或业务规则。

### 开发流程

Agent 开始写入前需要确认当前工作分支来源，但通常无需询问用户；只有执行环境无法确定目标分支且写入存在风险时，才记录阻塞并请求决定。

### 测试与验收

已验证：

- 通用文档不再把临时开发分支当作固定工作分支；
- Work/Codex 推荐提示改用环境工作分支；
- `docs/README.md`、`docs/dev-process/README.md` 与 `docs/test-log/README.md` 明确分支选择和记录规则；
- 已知历史 dev/test 文件中的误导性固定分支已修正；
- 新规则已通过 Issue #15 推动持续执行；
- 两个误创建的临时空文件已删除，最终目录树无残留。

## 建议如何修改

- 在 `docs/README.md` 增加“分支选择与文档可移植性”；
- 在开发和测试模板中记录分支来源而不是预设分支；
- 删除 Work 交接文档中的固定规划分支及固定分支提示；
- 将历史进度与测试记录改为“当次执行环境工作分支”；
- 后续在文档检查脚本中检测通用文档里的误导性固定分支。
