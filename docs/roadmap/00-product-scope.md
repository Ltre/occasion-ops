# 产品范围与原则

## 1. 产品定义

OccasionOps 是面向红白事、节日、祭典、演出、庆典、宗族及社区活动的现场事务与资源流转管理系统。

系统管理的不是单一“账目”或“任务”，而是一场临时活动中不断发生的事实：谁在何时收了钱、交给谁、买了什么、物料去了哪里、任务由谁接手、商家完成到什么程度，以及哪些事项尚未闭环。

初代版本以**最简单、可核对、可追溯的资金流水记录**为唯一首要目标。采购、物料、任务、施工和 AI 不能阻塞第一个资金试点。

## 2. 核心用户

### 活动负责人

关注全局进展、资金位置、重大异常和待决策事项。

### 管账人与收礼人员

关注礼金归属、实际到账、资金转移、现金盘点、垫付报销和商家结算。

### 采购人与物料管理员

关注需求、询价、下单、付款、收货、领用、调拨、剩余和归还。

### 理事会成员、任务负责人和临时帮工

关注当前任务、现场位置、交接对象、所需资源和完成反馈。

### 场地、施工、装饰、车辆负责人

关注进场、进度、材料、区域、变更、验收、拆除和恢复。

### 外部商家与临时参与者

只需完成与自己有关的报价、到场、交付、收款、退款或交接记录，不应看到完整活动数据。

## 3. 核心场景

- 红包、礼金、帛金由多人代付、代收、合并转账或多次转交；
- 活动资金分散在多个账户、现金箱、家属和理事会成员手中；
- 采购的需求人、批准人、采购人、付款人、收货人和验收人不同；
- 现场人员先垫付，之后部分报销、合并报销或由他人代领；
- 转账被换为现金，再经过多人交接后用于零星支出；
- 物料直接送到使用区域，未经过正式仓库；
- 任务临时换人，原负责人不在场，需要快速完成责任交接；
- 商家增项、减项、延误、退货、押金和尾款在活动后继续结算；
- 网络不稳定，现场只来得及拍照、说一句话或记一个金额；
- 临时参与者不愿安装应用，但可以通过微信小程序、链接或二维码进入；
- 中国大陆和海外用户需要就近访问附件，不应被固定到同一海外或国内存储区域。

## 4. 产品边界

### 4.1 初代资金 MVP

初代优先实现：

- 最小活动与成员管理；
- 统一资金流水；
- 多账户、多现金箱和资金位置；
- 收入、支出和内部转移；
- 垫付、报销和备用金；
- 理论余额、盘点、待确认和异常；
- 附件证据、人工确认和审计历史；
- 移动端极简记录；
- 弱网草稿、幂等和防重复。

### 4.2 资金试点后扩展

- 完整礼金归属与实际到账；
- 采购、到货、退货退款和供应商；
- 物料领用、调拨、归还和当前位置；
- 任务分派、转交和完成；
- 临时人员受限入口；
- 场地、施工、车辆和其他活动运营能力；
- AI 自动整理、匹配和异常提示。

### 4.3 暂不纳入

- 正式会计总账、税务申报和法定财务凭证；
- 通用票务、售票和大规模报名；
- 完整 ERP、HR、薪资或专业工程管理；
- 代替银行、支付平台或电子发票平台；
- 由 AI 自动批准付款、报销或责任认定；
- 初代同时开发 Android 和 iOS；
- 初代建设全球多主存储或默认跨境复制。

## 5. 客户端平台范围

### 5.1 首期正式客户端

首期同时支持：

1. **PWA**；
2. **微信小程序**。

两端共同承担初代资金流水核心功能，并使用同一套服务端：

- API 契约；
- 资金语义；
- 权限和活动范围；
- 审计和更正规则；
- 幂等与重复提交规则；
- 核心业务场景和验收标准。

两端 UI 可以按平台优化，不要求像素级一致。平台登录、拍照、扫码、本地存储、上传和通知通过适配层处理，不能在两个客户端中分别重新定义业务规则。

### 5.2 后续客户端

Android 与 iOS 在以下条件出现后评估：

- PWA 或微信小程序无法满足明确的离线、后台、设备能力或性能需求；
- 需要应用商店、企业部署或设备管理；
- 服务端 API、领域模型和跨端测试已经稳定；
- 真实用户规模和场景证明原生端投入合理。

Android/iOS 不阻塞初代资金 MVP 和首轮真实活动试点。

完整技术方向见 `docs/tech/client-platform-strategy.md`。

## 6. 区域与对象存储范围

OccasionOps 主要面向中国大陆用户，因此：

- 中国大陆生产环境优先使用国内区域和阿里云 OSS、腾讯云 COS 等国内对象存储；
- 海外环境可以选择 AWS S3、Cloudflare R2 或其他就近国际对象存储；
- 业务代码使用统一对象存储 Provider，不绑定单一厂商；
- 不假设所有厂商完整兼容 AWS S3；
- 附件默认私有，由服务端鉴权后签发短期凭证；
- 部署环境必须明确主数据区域；
- 不默认跨境复制；
- 厂商或区域迁移必须可审计、可重试并校验完整性。

首期只需落地一个国内生产 Provider 和本地开发 Provider，同时验证一个国际 Provider 的契约；不要求同时运行多个生产云厂商。

完整技术方向见 `docs/tech/object-storage-and-region-strategy.md`。

## 7. 设计原则

1. **资金优先**：初代研发资源优先用于资金流水记录和正确性；
2. **事实优先**：先留下发生过什么，再补齐分类和字段；
3. **流水优先**：业务视图从流水聚合，不让用户重复记多套账；
4. **位置优先**：资金和物料始终有当前位置或当前保管人；
5. **关联优先**：转账、采购、到货、领用和报销应能串成过程；
6. **追加修正**：重要记录通过更正、作废和补充处理，不无痕覆盖；
7. **现场优先**：常用操作适合单手、移动、嘈杂和弱网环境；
8. **最小可见**：临时人员只接触完成任务所必需的数据；
9. **服务端守则**：客户端不决定最终资金方向、余额和权限；
10. **区域可选**：部署和存储按用户区域选择，但业务规则保持一致；
11. **人工兜底**：系统和 AI 无法判断时进入待整理队列，而不是阻塞记录。

## 8. 产品成功指标

初代试点重点验证：

- 80% 以上现场资金记录可在 10 秒内完成；
- 绝大多数记录无需输入长文本或理解会计术语；
- 活动负责人能查看每个资金位置的理论余额；
- 内部转移不重复计入收支；
- 垫付、备用金、押金和退款有明确未结清列表；
- 待确认记录不无提示进入正式余额；
- PWA 与微信小程序对同一资金操作产生相同业务语义；
- 弱网和跨端重试不生成重复流水；
- 附件权限、存储区域和访问可追溯；
- 中国大陆试点不依赖海外对象存储；
- AI 建议不会覆盖原始记录，所有关键修改可审计。

## 9. 开发任务

### P0

- 定义资金领域术语和状态；
- 建立最小活动、成员、角色、流水、附件和资金位置模型；
- 明确修改、审计、幂等和恢复原则；
- 建立至少 30 个正常与异常资金场景；
- 建立 PWA 与微信小程序共享 API 契约；
- 建立对象存储 Provider 接口和附件元数据模型。

### P1

- 完成 PWA 与微信小程序基础壳；
- 完成收、支、转和确认摘要；
- 完成余额、待确认、更正、作废和审计；
- 完成垫付、报销和备用金；
- 完成盘点、异常和未结事项；
- 完成国内对象存储主适配器；
- 完成跨端资金场景和存储契约测试。

### P2

- 增加完整礼金、采购、物料和临时协同；
- 加固 PWA 与小程序弱网和附件体验；
- 验证国际对象存储和海外部署；
- 引入 AI 结构化、自动关联和异常提示；
- 根据真实需求评估 Android/iOS。

## 10. 验收标准

- 产品范围能通过至少三类活动案例验证；
- 核心模型不依赖婚礼、葬礼等单一流程；
- 初代资金范围和后续扩展边界清楚；
- 首期客户端明确为 PWA 与微信小程序；
- Android/iOS 阶段和触发条件清楚；
- 国内与海外对象存储选择和数据区域原则清楚；
- 业务规则不依赖特定客户端或存储厂商；
- 所有专题技术文档可追溯到本文件定义的目标和原则。
