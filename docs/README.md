# OccasionOps 文档使用说明

`docs/` 是 OccasionOps 的产品事实、开发计划、实时进度、测试证据和需求变更记录中心。

所有参与项目的人员和 Agent，包括 ChatGPT Work、Codex 及其他自动化工具，在开始工作前都必须先阅读本文件，并按这里定义的流程维护文档。

## 1. 目录职责

```text
docs/
├── README.md                  # 本文件：docs 总入口和工作规则
├── roadmap/                   # 已确认需求、开发计划和需求变更
│   ├── README.md              # roadmap 索引、当前优先级与执行入口
│   └── change-requests/       # 已确定需求变更的差异与影响记录
├── dev-process/               # 每项开发工作的实时进度记录
├── test-log/                  # 与开发进度对应的实时测试记录
├── domain/                    # 领域术语、流水类型、状态与关联关系
└── tech/                      # 技术架构、实现约束和技术决策
```

## 2. 事实来源优先级

发生冲突时，按以下顺序处理：

1. 项目所有者最新明确指令；
2. 已批准的变更申请、ADR 或 GitHub Issue 决策；
3. `docs/roadmap/` 中已更新的需求与开发计划；
4. `docs/domain/` 和 `docs/tech/` 中已确认的设计；
5. `docs/dev-process/` 中记录的当前实现状态；
6. `docs/test-log/` 中保存的验证结果；
7. 现有代码行为；
8. 根目录 README 的项目介绍。

代码与已确认需求冲突时，不得默认代码正确。应先记录差异，再决定修改需求、迁移数据或调整实现。

## 3. Agent 开始或恢复工作前必须读取

至少读取：

1. `docs/README.md`；
2. `docs/roadmap/README.md`；
3. 与当前功能相关的 roadmap 文件；
4. `docs/roadmap/change-requests/` 中相关且已批准的变更；
5. `docs/dev-process/` 中该功能最新的进度文件；
6. `docs/test-log/` 中对应的测试文件；
7. 相关 GitHub Issue、PR、commit 和现有代码。

如果还没有对应的开发进度或测试记录，应在实际修改代码前创建。

## 4. 分支选择与文档可移植性

`docs/` 会合并到 `main`，并随未来创建的任何分支继续使用。因此，通用说明、roadmap、模板和 Agent 指引不得绑定某个临时开发分支。

### 4.1 分支选择优先级

执行文件修改时按以下顺序确定工作分支：

1. 项目所有者在**当次提示**中明确指定的分支；
2. Codex 环境中已经配置、检出或选定的工作分支；
3. 其他执行 Agent 或集成当前已经选定的工作分支或目标分支。

用户当次提示没有指定分支时，不需要重复询问；应使用执行环境已经指定的工作分支。

只有执行环境无法确定任何目标分支，并且继续写入可能造成错误时，才应记录阻塞并请求项目所有者决定。

### 4.2 禁止事项

除非项目所有者明确要求，不得：

- 因历史文档中出现过某个分支名，就切换到该分支；
- 默认把修改写入 `main`；
- 擅自创建新分支；
- 将一次任务的临时分支写成项目永久规则；
- 让文档中的分支表述覆盖 Codex 或执行环境的当前分支设置。

### 4.3 文档如何记录分支

- 通用文档使用“当前工作分支”“执行环境指定分支”“目标分支”等表述；
- `dev-*` 和 `test-*` 可以记录当次工作分支，但不得将其描述成后续任务的默认分支；
- 实际修改的分支、提交和合并关系优先通过 PR、commit 和 Issue 追溯；
- 只有分支名本身属于需求、迁移或历史证据时，才在文档中保留具体分支，并注明其适用上下文。

## 5. 开发进度记录

每项实现工作都必须在 `docs/dev-process/` 中维护实时进度文件。

文件名格式：

```text
dev-YYMMDD-功能名称或描述.md
```

示例：

```text
dev-260722-money-quick-entry.md
```

记录必须包含：

- 目标、范围和非目标；
- 关联 roadmap、变更申请、Issue、PR 和 commit；
- 当前状态和已完成事项；
- 正在进行的工作；
- 已修改或计划修改的文件；
- 关键决策、风险和阻塞；
- 下一步可直接执行的动作；
- 对应测试记录路径；
- 当次工作分支的来源，例如“用户指定”或“执行环境选定”，但不要把它写成通用默认值。

开发过程中应持续更新，而不是结束后一次性补写。

## 6. 测试记录

每项开发工作都必须在 `docs/test-log/` 中维护对应测试记录。

文件名格式：

```text
test-YYMMDD-功能名称或描述.md
```

开发进度与测试记录应使用相同的日期和功能描述，例如：

```text
docs/dev-process/dev-260722-money-quick-entry.md
docs/test-log/test-260722-money-quick-entry.md
```

测试记录必须包含：

- 对应开发进度文件；
- 测试范围与环境；
- 自动化测试命令及结果；
- 单元、集成、端到端和人工验证情况；
- 正常、异常、权限、幂等、并发、恢复等关键场景；
- 失败项、缺陷、未测项和原因；
- 测试证据、相关 commit、PR 或 CI；
- 最终结论和是否达到验收标准。

没有对应测试记录的功能，不得标记为完成。

## 7. 已确定需求变更

当需求变更已经确定，不再只是讨论或候选方案时，必须执行以下步骤：

1. 在 `docs/roadmap/change-requests/` 新建变更申请；
2. 明确记录：
   - 原来的需求是什么；
   - 改动后的需求是什么；
   - 变更原因；
   - 对产品、数据、接口、迁移、测试和进度的影响；
   - 可选：建议如何修改实现；
3. 同一提交或紧随其后的提交中，更新受影响的原 roadmap 文件；
4. 创建或更新 GitHub Issue，推动设计、实现、测试和必要迁移；
5. 在开发进度与测试记录中引用该变更申请。

变更申请用于保存差异和决策历史。最新有效需求必须体现在原 roadmap 文件中，不能只存在于 change request 中。

## 8. 主动推进规则

Agent 不应只输出建议后停止。只要不存在必须由项目所有者决定的阻塞项，就应按以下循环主动推进：

1. 读取事实来源；
2. 按本文件规则确定当前工作分支；
3. 确认当前最小可交付切片；
4. 创建或更新开发进度和测试记录；
5. 完成设计、代码、测试和文档；
6. 回写进度、测试结果、Issue 和必要的 roadmap；
7. 继续执行下一条明确且无阻塞的任务。

如果必须暂停，开发进度文件必须留下精确的下一步、阻塞原因和恢复条件，不能只写“待继续”。

## 9. 工作状态建议

开发进度文件建议使用：

- `planned`：范围已确定，尚未开始；
- `in-progress`：正在实现；
- `blocked`：存在明确阻塞；
- `in-review`：实现完成，等待评审或验证；
- `completed`：需求、实现、测试和文档均已完成；
- `cancelled`：经确认不再执行。

测试记录建议使用：

- `not-started`；
- `in-progress`；
- `passed`；
- `failed`；
- `blocked`；
- `partial`。

## 10. 完成定义

一项功能只有同时满足以下条件，才可以标记完成：

- roadmap 或已批准变更中的验收标准已满足；
- 代码和必要的数据迁移已完成；
- 自动化测试通过，或未通过项已有明确 Issue；
- 对应 `docs/test-log/test-*.md` 已更新；
- 对应 `docs/dev-process/dev-*.md` 已更新为 `completed`；
- 相关 Issue、PR、commit 和文档互相链接；
- 未完成事项已拆为独立 Issue，而不是隐藏在备注中；
- 没有未说明的权限、审计、幂等、恢复、兼容或分支风险。

## 11. 总体禁止事项

- 不得只在聊天、Issue 评论或 PR 描述中保存关键需求；
- 不得在未记录变更申请的情况下悄悄改变已确认需求；
- 不得只改代码而不更新开发进度与测试记录；
- 不得用“测试通过”代替具体命令、场景和结果；
- 不得无痕覆盖已确认的资金、权限或审计规则；
- 不得用历史文档中的固定分支覆盖执行环境的工作分支；
- 不得因 AI、采购、库存或任务功能未完成而阻塞初代资金流水主线。
