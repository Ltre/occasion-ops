# 服务端技术架构

> 状态：当前技术方向  
> 适用阶段：MVP 至早期生产阶段  
> 更新日期：2026-07-22

## 1. 结论

OccasionOps 采用以下技术基线：

- **首期客户端：PWA + 微信小程序**；
- **后续客户端：Android / iOS，在首期试点稳定后评估**；
- **主语言与框架：TypeScript + NestJS**；
- **架构形态：模块化单体**；
- **主数据库：PostgreSQL**；
- **异步任务：Redis + BullMQ**；
- **文件存储：项目自有对象存储抽象，国内云优先、国际存储可选**；
- **AI 接入：主服务调用模型 API，必要时增加独立 Worker**；
- **Python：不作为主服务端语言，仅在专项计算需求明确时引入**。

正式业务事实以 PostgreSQL 为准。Redis、对象存储、客户端本地草稿和第三方平台都不能保存唯一一份资金、权限或审计事实。

客户端和存储的专项决策见：

- [客户端平台策略](./client-platform-strategy.md)；
- [对象存储与区域部署策略](./object-storage-and-region-strategy.md)。

## 2. 架构目标

项目初期的核心挑战不是高并发，而是：

- 资金流水方向和余额正确；
- 内部转移不重复计入收支；
- 垫付、报销、备用金、押金和退款能够闭环；
- 多人、多角色和临时人员的数据权限；
- 不同活动之间的数据隔离；
- 弱网重试、重复提交和并发修改；
- 更正、作废和完整审计；
- 图片、票据、语音和附件的安全存储；
- PWA 与微信小程序使用相同业务规则；
- 国内和海外部署能够选择合适的对象存储区域；
- AI、OCR、导入和报表等耗时任务可靠执行。

架构优先保证业务正确性、可追溯性、低门槛现场体验和开发效率，不提前为假设中的超大规模设计微服务或复杂缓存。

## 3. 总体架构

```text
PWA                     微信小程序
 │                          │
 └────────── 同一套业务 API ──────────┘
                    │
                    ▼
          NestJS 模块化单体
          ├── 身份与活动范围
          ├── 同步 API 与权限校验
          ├── 领域规则与数据库事务
          ├── 统一流水、资金与审计
          ├── 附件授权与存储路由
          ├── 后台任务创建
          └── 轮询 / WebSocket 进度
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   PostgreSQL     Redis       对象存储适配层
   正式事实       BullMQ      ├── 阿里云 OSS
                  │           ├── 腾讯云 COS
                  ▼           ├── AWS S3 / R2
                Worker        └── 本地开发存储
          ├── OCR 与图片处理
          ├── AI 候选整理
          ├── 导入导出
          ├── 迁移与校验
          └── 通知和失败重试
```

API、Worker 和共享包可以位于同一 Monorepo。初期可部署在同一台服务器或同一区域的少量实例中；只有出现实际资源隔离需求时再拆分进程或服务。

## 4. 客户端边界

PWA 与微信小程序是首期正式客户端，两端必须共享：

- API 契约；
- 领域类型和状态；
- 金额与资金方向校验；
- 确认摘要生成规则；
- 幂等键和重复提交语义；
- 权限、审计和错误码；
- 跨端业务场景测试。

业务规则不能分别实现在两个客户端中。关键复合操作，例如内部转移、垫付、报销和备用金结算，必须由服务端命令在一个数据库事务中完成。

平台特有能力通过适配层隔离，例如登录、本地存储、拍照、扫码、文件上传、网络状态和通知。

Android/iOS 不阻塞 MVP；启动条件见客户端平台策略。

## 5. 模块化单体

建议模块：

```text
occasion        活动、阶段和活动范围
identity        成员、角色、登录渠道、临时身份和授权
ledger          统一流水及流水关联
finance         资金位置、收支、内部转移、垫付、报销和结算
gift            礼金归属、付款人与实际到账
procurement     采购需求、订单和供应商
inventory       物料、位置、领用和归还
task            人员任务、交接、场地和施工
attachment      附件元数据、上传会话和访问授权
storage         存储配置、Provider 接口、迁移和校验
audit           更正、作废、版本和审计
ai-workbench    AI 候选、匹配、确认和驳回
job             后台任务、进度、结果和重试
```

模块化用于控制业务边界，不代表初期需要拆成微服务。

## 6. PostgreSQL 的职责

PostgreSQL 是系统唯一正式业务事实来源，保存：

- 活动、成员、角色和数据范围；
- 统一流水和关联关系；
- 收支、内部转移、资金位置和余额依据；
- 垫付、报销、备用金和商家结算；
- 礼金、采购、物料、任务及其状态；
- 附件元数据、存储配置和对象引用；
- AI/OCR 候选与人工确认结果；
- 后台任务状态和执行结果；
- 更正、作废和审计历史。

涉及多条正式记录的操作必须使用事务。不能出现内部转移只扣来源未加目标、报销只付款未减少待偿义务、附件已关联但上传未确认等部分成功状态。

### 活动数据隔离

活动范围内的数据显式包含 `occasion_id` 或可追溯到活动：

- 服务端根据有效成员身份或临时授权判断访问；
- 查询和写入统一施加活动范围；
- 权限同时限制操作和可见数据；
- 不能相信客户端传入的活动标识作为最终权限依据；
- 审计记录保留操作者、活动、时间和依据。

是否采用 PostgreSQL Row-Level Security，在权限模型与性能测试后决定。

## 7. Redis 与 BullMQ

Redis 主要用于可靠异步任务，不用于保存正式业务事实，也不作为资金、库存、权限或审计的业务查询缓存。

适合进入队列的任务：

- OCR、图片压缩和缩略图；
- AI 候选生成和批量整理；
- 批量导入导出；
- 报表和活动归档；
- 对象存储迁移、哈希校验和孤儿检查；
- 通知、定时任务和第三方失败重试。

队列约束：

- 消息只携带任务 ID 和必要路由信息；
- Worker 执行前从 PostgreSQL 读取最新状态；
- 结果和状态写回 PostgreSQL；
- 任务必须幂等；
- 区分可重试错误与业务错误；
- AI/OCR 只能创建候选，不能绕过人工确认写入关键资金流水；
- Redis 故障不能造成正式数据丢失。

## 8. 对象存储

附件本体保存到对象存储，PostgreSQL 保存对象元数据和业务关联。

### Provider 抽象

业务模块依赖项目统一的 `ObjectStorageProvider`，不直接依赖阿里云、腾讯云、AWS 或其他厂商 SDK。

首期适配目标：

- 国内生产：阿里云 OSS 或腾讯云 COS 二选一作为首个主适配器；
- 本地开发：文件系统或本地对象存储适配器；
- 国际能力：AWS S3 或 Cloudflare R2 的契约验证适配器；
- 其他厂商按相同接口扩展。

不能假设所有国内对象存储完整兼容 AWS S3；S3 只是一个 Provider 实现。

### 存储区域

- 中国大陆生产环境默认使用国内区域和国内云存储；
- 海外部署按用户所在地选择海外区域和国际存储；
- 一个部署环境有明确主数据区域；
- 不默认跨境复制附件；
- 跨区域复制、迁移和删除必须可审计并校验完整性。

### 安全

- 存储桶默认私有；
- 服务端鉴权后签发短期上传或下载凭证；
- 对象键不包含敏感个人信息；
- 密钥使用秘密管理或临时凭证；
- 附件记录大小、类型、哈希、活动、上传人、状态和存储配置；
- 不保存永久公网 URL 作为唯一对象引用；
- 派生文件继承原附件权限。

详细要求见对象存储与区域部署策略。

## 9. 上传与处理流程

```text
客户端请求上传
→ 服务端校验活动、权限、类型和大小
→ 创建上传会话、对象键和幂等标识
→ 客户端直传或受控上传
→ 服务端确认对象存在并校验元数据
→ PostgreSQL 标记附件已上传
→ Worker 执行压缩、缩略图、OCR 或安全检查
→ 结果写回数据库
```

PWA 与微信小程序使用相同的附件状态语义，但可采用不同的本地上传实现。

## 10. 同步与异步边界

同步执行：

- 普通查询和小型写入；
- 创建或确认单条资金流水；
- 权限和领域规则校验；
- 必须立即向用户返回成功或失败的原子操作；
- 创建附件上传会话和确认结果。

异步执行：

- AI/OCR；
- 大批量导入导出；
- 图片和附件后处理；
- 存储迁移与完整性校验；
- 报表、归档、通知和可重试第三方调用。

正式写入不能仅“放进队列就算完成”。客户端必须获得可查询的任务或业务状态。

## 11. 初期部署

中国大陆首期生产建议：

```text
PWA 静态站点 / Web 服务
微信小程序
1 个 NestJS API 实例
1 个 Worker 进程
1 个 PostgreSQL 实例
1 个 Redis 实例
1 个国内对象存储桶（OSS 或 COS）
```

API、数据库、Redis、Worker 和存储尽量位于同一云或相近区域，减少附件上传处理和服务间网络的不确定性。

海外环境可以采用相同应用架构，但选择就近数据库、计算和国际对象存储。

当前不需要：

- 微服务拆分；
- Kubernetes；
- Redis Cluster 或 Sentinel；
- 业务查询缓存；
- 多数据库分片；
- 全球对象存储多主；
- 默认跨境复制；
- 同时开发 Android 和 iOS；
- 为 AI 单独建立 Python 主服务。

## 12. 测试基线

至少包含：

- PWA 与微信小程序 API 契约一致性；
- 跨端收、支、转、垫付、报销和备用金场景；
- 重复点击、弱网重试和幂等；
- 权限和跨活动越权；
- 资金余额可从流水重建；
- 国内对象存储适配器契约测试；
- 国际对象存储适配器契约验证；
- 短期凭证、私有访问和附件权限；
- 上传失败恢复、重复完成回调和对象不存在；
- 数据库备份恢复后附件引用完整；
- 存储迁移的哈希和数量校验。

## 13. 演进触发条件

只有出现真实问题时增加复杂度：

- PWA 或微信小程序无法满足明确需求时，评估 Android/iOS；
- AI/OCR 挤占 API 资源时，独立 Worker 或横向扩容；
- 数据库优化后仍有明确查询瓶颈时，评估缓存；
- 不同团队独立发布或故障域成为实际问题时，评估微服务；
- 海外用户规模和访问数据证明需要独立海外区域时，建立区域部署；
- 厂商迁移或合规要求出现时，执行对象存储迁移流程；
- TypeScript 不适合专项算法时，增加 Python Worker。

## 14. 当前技术基线

```text
首期客户端      PWA + 微信小程序
后续客户端      Android / iOS 按真实需求启动
主服务端        TypeScript + NestJS
架构            模块化单体
正式数据        PostgreSQL
异步任务        Redis + BullMQ
国内附件        OSS 或 COS，经统一 Provider 接口
海外附件        S3 / R2 等，经统一 Provider 接口
附件权限        私有存储 + 服务端鉴权 + 短期凭证
实时进度        轮询起步，必要时使用 WebSocket
AI              模型 API + 候选记录 + 人工确认
Python          按专项需求增加 Worker
部署            国内与海外按区域独立选择，按实际瓶颈演进
```

这套基线让初期资源集中在资金流水正确性和低门槛现场体验，同时为中国大陆与海外用户保留合适的客户端和存储部署选择。
