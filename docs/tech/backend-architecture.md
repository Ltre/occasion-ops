# 服务端技术架构

> 状态：当前技术方向  
> 适用阶段：MVP 至早期生产阶段  
> 更新日期：2026-07-22

## 1. 结论

OccasionOps 的服务端采用以下技术方向：

- **主语言与框架：TypeScript + NestJS**
- **架构形态：模块化单体**
- **主数据库：PostgreSQL**
- **异步任务：Redis + BullMQ**
- **文件存储：S3 兼容对象存储**
- **AI 接入：由主服务调用模型 API；必要时增加独立 Worker**
- **Python：暂不作为主服务端语言，仅在出现专项计算需求时引入**

Redis 可以从初期加入，但主要用于可靠的异步任务、批量处理、延迟任务和失败重试，**不是为了给业务查询做缓存，也不是因为系统需要应付高并发**。

礼金、资金、采购、物料、任务、权限、审计和任务执行状态等正式数据，均以 PostgreSQL 中的数据为准。Redis 不保存任何唯一一份业务事实。

## 2. 选型背景

OccasionOps 面向红白事、节日、祭典、演出、庆典等临时组织活动。单场活动的使用人数通常不到 10 人，大型团队一般也只有几十人，因此系统初期不存在必须依赖分布式架构或复杂缓存体系的并发压力。

项目真正需要优先处理的是：

- 多人、多角色和临时人员的数据权限；
- 不同活动之间的数据隔离；
- 礼金归属与实际到账的分离；
- 真实收支与内部资金转移的区分；
- 采购、付款、到货、验收和物料流转之间的关联；
- 垫付、备用金、报销、退款和押金的闭环；
- 任务交接、状态变化和责任追溯；
- 弱网重试、重复提交和并发修改；
- 更正、作废及完整审计；
- AI、OCR、批量导入等耗时任务的可靠处理。

因此，架构设计以**业务正确性、可追溯性和开发效率**为核心，而不是提前为假设中的大规模并发设计。

## 3. 总体架构

```text
客户端 / PWA
    │
    ▼
NestJS 模块化单体
    ├── 同步 API 与权限校验
    ├── 领域规则与事务
    ├── WebSocket / 进度查询
    ├── AI 与 OCR 任务创建
    └── BullMQ 任务生产者
          │
          ▼
       Redis
          │
          ▼
       Worker
    ├── AI 结构化整理
    ├── OCR 与附件处理
    ├── 批量导入和导出
    ├── 报表及归档生成
    └── 提醒、通知与失败重试

PostgreSQL：正式业务数据、任务状态、执行结果和审计记录
对象存储：票据、图片、语音、附件和活动归档
```

初期可以将 API 和 Worker 放在同一代码仓库，并复用领域模型、DTO 和基础设施模块。部署时可以先运行在同一台服务器上；出现耗时任务互相影响时，再把 Worker 独立为单独进程或容器，无需拆分业务服务。

## 4. 为什么主服务端选择 TypeScript + NestJS

### 4.1 前后端共享类型语言

前端、服务端、API DTO、表单校验以及 AI 结构化输出都可以使用 TypeScript 描述，能够减少字段含义、枚举值和状态定义不一致的问题。

这对 OccasionOps 尤其重要，因为统一流水、资金位置、物料位置、关联关系和状态转换都会包含大量明确的类型约束。

### 4.2 适合模块化单体

NestJS 提供模块、依赖注入、验证、权限守卫、拦截器、WebSocket 和任务队列等常用能力，适合在单体应用内保持清晰的业务边界。

初步模块可按以下方式组织：

```text
occasion        活动、阶段和活动范围
identity        成员、角色、临时身份和授权
ledger          统一流水及流水关联
finance         资金位置、垫付、报销和结算
gift            礼金归属、付款人与实际到账
procurement     采购需求、订单和供应商
inventory       物料、位置、领用和归还
task            人员任务、交接、场地和施工
attachment      图片、语音、票据和证据
audit           更正、作废、版本和审计
ai-workbench    AI 候选、匹配、确认和驳回
job             后台任务、进度、结果和重试
```

模块化是为了控制业务边界，不代表初期需要拆成微服务。

### 4.3 AI 不决定主服务端语言

调用模型 API、提交 OCR 任务、要求结构化输出、校验模型结果以及消费异步任务，TypeScript 都可以完成。

AI 生成的内容应先进入候选区，由领域规则校验并经人工确认后，才能成为正式流水。这里更重要的是事务、权限和审计，而不是 Python 生态。

只有出现以下需求时，才考虑增加 Python Worker：

- 自建或微调模型；
- 复杂图像处理或计算机视觉；
- 大规模数据分析、训练或评估；
- 必须依赖 Python 生态的专用算法。

即使增加 Python Worker，NestJS 仍作为主服务端和业务事实入口。

## 5. PostgreSQL 的职责

PostgreSQL 是系统唯一的正式业务数据来源，负责保存：

- 活动、成员、角色和授权范围；
- 统一流水及其关联关系；
- 礼金、收支、内部转移和资金位置；
- 采购、订单、供应商和结算；
- 物料数量、位置、保管人和流转；
- 任务、交接、场地、施工和验收；
- AI/OCR 候选记录及人工确认结果；
- 后台任务状态、执行次数和最终结果；
- 更正、作废和审计历史。

涉及多条正式记录的操作必须使用数据库事务保证一致性。例如，一次报销可能同时影响垫付余额、活动资金位置、关联流水和审计记录，这些更新不能部分成功。

### 5.1 活动数据隔离

不同活动的数据在业务上必须隔离，但初期不需要为每场活动单独部署服务或数据库。

建议在所有活动范围内的数据中显式包含 `occasion_id`，并在服务端统一执行活动范围校验：

- 用户必须先拥有该活动的有效成员身份或临时授权；
- 查询和写入必须带入当前活动范围；
- 权限不仅限制功能，也限制可见数据；
- 管理员、管账人员、采购人员和临时人员的数据范围可以不同；
- 审计记录必须保留操作者、活动、时间和操作依据。

是否进一步采用 PostgreSQL Row-Level Security，应在权限模型定稿和实现阶段评估。无论是否使用 RLS，服务端都不能依赖客户端传入的活动标识来决定最终权限。

数据隔离解决的是权限和业务边界，不等于性能优化，也不会从原理上消除系统总负载；但按当前预计规模，正常的索引和查询设计已经足够。

## 6. Redis 与 BullMQ 的定位

### 6.1 初期可以引入的原因

是否需要队列主要取决于任务是否耗时、是否需要重试和是否允许用户一直等待，而不是取决于在线人数。

即使一场活动只有 3 人，一次上传 100 张票据也可能产生大量 OCR、图片处理和 AI 整理任务。将这些任务放入后台执行，可以避免接口长时间阻塞，并保留失败重试和处理进度。

初期适合进入队列的任务包括：

- 批量导入礼金、采购和物料数据；
- 批量处理票据图片和 OCR；
- 根据语音、图片生成 AI 候选记录；
- 图片压缩和缩略图生成；
- 批量生成报表、对账单和活动归档；
- 定时提醒和通知发送；
- 调用第三方服务失败后的自动重试。

### 6.2 明确不承担的职责

初期不使用 Redis 缓存以下业务数据：

- 活动详情；
- 礼金、资金和库存余额；
- 统计报表结果；
- 用户和活动权限；
- 正式流水；
- AI/OCR 的唯一结果。

这些内容一律从 PostgreSQL 获取。这样可以避免数据库已经更新、缓存仍是旧数据的一致性问题，尤其不能让资金和物料视图依赖可能过期的缓存。

### 6.3 队列设计约束

- 队列消息尽量只携带任务 ID、记录 ID 和必要的路由信息，不塞入大量业务数据；
- Worker 开始执行前，从 PostgreSQL 读取最新状态和输入；
- Worker 的最终结果和任务状态写回 PostgreSQL；
- 所有任务必须设计为幂等，重复消费不能造成重复记账、重复入库或重复通知；
- 创建任务时应使用业务幂等键，防止客户端重试产生多个等价任务；
- AI/OCR 结果只能创建候选记录，不能绕过人工确认直接写入关键正式流水；
- 批量任务必须记录总数、成功数、失败数、部分完成状态和可重试项；
- 应区分可重试错误与业务错误，避免对永久失败任务无限重试；
- Redis 故障不能造成正式业务数据丢失；必要输入和处理状态必须可从 PostgreSQL 恢复。

初期使用单实例 Redis 即可，不需要集群、哨兵或多地域部署。

## 7. 同步与异步操作边界

优先同步执行：

- 普通增删改查；
- 创建或确认单条流水；
- 资金、礼金、物料和任务的状态变更；
- 必须立即向用户返回成功或失败的事务操作；
- 权限校验和领域规则校验。

优先异步执行：

- 运行时间不可预测的 AI 或 OCR 调用；
- 大批量导入、导出和附件处理；
- 可在后台完成的报表和归档；
- 需要延迟执行、定时执行或失败重试的任务；
- 不应占用 API 请求生命周期的第三方调用。

正式业务写入不能简单地“丢进队列后就算完成”。客户端应先获得明确的任务记录，随后通过轮询或 WebSocket 查看任务进度、部分失败和最终结果。

## 8. 对象存储

票据、图片、语音、视频、聊天截图、报价单和归档文件不直接存入 Redis，也不建议将大文件二进制内容直接放入 PostgreSQL。

对象存储负责保存文件本体；PostgreSQL 保存：

- 对象键和文件元数据；
- 所属活动与上传人；
- 文件用途和关联流水；
- 哈希值、大小和 MIME 类型；
- 处理状态、识别结果和审计信息；
- 生命周期和删除状态。

访问附件时应由服务端校验活动和数据权限，再签发短期访问地址，不能把对象存储设为永久公开。

## 9. 初期部署建议

初期保持部署简单：

```text
1 个 NestJS API 实例
1 个 Worker 进程
1 个 PostgreSQL 实例
1 个 Redis 实例
1 个 S3 兼容对象存储
```

API 与 Worker 可以来自同一代码仓库和同一构建产物，但使用不同启动命令。开发环境可以进一步合并运行，生产环境再拆成独立进程，以免 OCR 或批量任务占用 API 资源。

当前不需要：

- 微服务拆分；
- Kubernetes；
- Redis Cluster 或 Sentinel；
- 业务查询缓存；
- 多数据库分片；
- 每场活动单独数据库；
- 为单场几十人设计复杂的水平扩容；
- 为 AI 单独建立 Python 主服务。

## 10. 后续演进触发条件

只有出现明确问题时才增加复杂度。

### 考虑业务缓存

满足以下一种或多种情况后再评估：

- 数据库慢查询经过索引和 SQL 优化后仍影响体验；
- 同一统计结果被高频重复读取且允许短暂过期；
- 已经能够定义清楚缓存失效规则；
- 有监控数据证明缓存收益大于一致性成本。

### 考虑拆分 Worker 或横向扩容

- AI/OCR 任务明显挤占 API 资源；
- 队列等待时间持续超出产品目标；
- 不同任务需要独立的并发、超时或资源限制；
- 单机故障恢复时间不能满足要求。

### 考虑微服务

- 模块由不同团队独立维护和发布；
- 单体发布频率或故障域已经成为实际瓶颈；
- 某个模块需要完全不同的扩容或运行环境；
- 已有足够的监控、自动化部署和运维能力支持分布式系统。

### 考虑 Python Worker

- 已确认存在 TypeScript 不适合承担的模型训练、图像算法或数据科学任务；
- Python 依赖带来的收益明显高于多语言部署和维护成本。

## 11. 当前技术基线

```text
主服务端        TypeScript + NestJS
架构            模块化单体
正式数据        PostgreSQL
异步任务        Redis + BullMQ
附件文件        S3 兼容对象存储
前端            TypeScript，优先 PWA
实时进度        轮询起步，必要时使用 WebSocket
AI              模型 API + 候选记录 + 人工确认
Python          按专项需求增加 Worker
部署            单区域、少实例、按实际瓶颈演进
```

这套基线允许初期快速开发，同时保留可靠处理批量任务和 AI/OCR 任务的能力。它不以高并发为假设，也不提前引入微服务和业务缓存的额外复杂度。
