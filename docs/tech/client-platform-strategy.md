# 客户端平台策略

> 状态：当前技术方向  
> 适用阶段：MVP 至早期生产阶段  
> 更新日期：2026-07-22

## 1. 结论

OccasionOps 客户端按以下顺序推进：

1. **PWA**：首期正式客户端；
2. **微信小程序**：首期正式客户端；
3. **Android 原生或跨平台应用**：资金 MVP 和现场试点稳定后评估；
4. **iOS 原生或跨平台应用**：资金 MVP 和现场试点稳定后评估。

PWA 与微信小程序不是“主端和临时端”的关系。两者在首期都需要支持核心资金流水能力，并共享同一套服务端 API、领域规则、权限、审计和测试标准。

Android 与 iOS 不阻塞第一个真实活动试点。只有当 PWA 或微信小程序无法满足明确的系统能力、性能、分发或设备集成需求时，才进入原生客户端开发。

## 2. 选择原因

### PWA

PWA 适合：

- 无需应用商店即可访问；
- 可通过链接或二维码进入；
- 便于临时采购人、帮工、司机和外部人员使用；
- 可快速迭代并覆盖桌面浏览器和移动浏览器；
- 适合管理端、对账、盘点和大屏信息查看；
- 可以逐步增加安装、离线壳和后台同步能力。

### 微信小程序

微信小程序适合主要面向中国大陆用户的现场环境：

- 用户通常已经安装微信；
- 无需额外下载完整应用；
- 二维码和群聊传播成本低；
- 适合临时参与者快速进入；
- 可利用微信登录、订阅消息、扫码和图片选择等平台能力；
- 对不熟悉浏览器或应用安装的用户更友好。

### 原生 Android/iOS 延后

初期不同时维护四套客户端，原因包括：

- 核心资金规则和现场交互仍需通过真实活动验证；
- 原生应用会增加构建、签名、发布、审核和版本兼容成本；
- 首期高频功能主要是表单、照片、扫码、弱网草稿和数据查看，PWA 与小程序可先验证；
- 过早开发原生端会分散资金流水正确性和低门槛体验的研发资源。

## 3. 首期功能一致性

PWA 与微信小程序至少共同支持：

- 活动选择与当前活动上下文；
- 成员身份和最小权限；
- “收到一笔”；
- “花了一笔”；
- “钱换地方了”；
- “我先垫付”；
- “给人报销”；
- “领／交备用金”；
- 待确认记录；
- 资金流水时间线；
- 资金位置和理论余额；
- 图片、截图和票据附件；
- 作废、更正和审计查看；
- 弱网草稿、失败重试和防重复提交。

某个平台暂时无法实现的能力必须：

1. 在对应 dev process 中记录差异；
2. 在 test log 中标明未测或不支持项；
3. 提供明确降级流程；
4. 不得默默改变资金含义或跳过关键确认。

## 4. 共享代码原则

建议采用 Monorepo，并共享以下 TypeScript 包：

```text
packages/
├── domain-types/        # 领域类型、状态、流水类型和校验规则
├── api-contract/        # API 请求响应、错误码和版本
├── money-rules/         # 金额、资金方向和确认摘要的纯函数
├── validation/          # 表单及服务端可复用校验
├── i18n/                # 文案、术语和多语言资源
└── test-scenarios/      # 跨端共享的业务场景和契约测试
```

客户端层可分别实现：

```text
apps/
├── pwa/
└── wechat-mini-program/
```

首期不要求两个客户端共享全部 UI 组件。优先共享领域规则、API 契约、状态机、格式化、校验和测试场景；平台 UI、路由、存储、登录、上传和通知通过适配层实现。

## 5. 平台适配层

客户端不得在业务页面中散落平台判断。建议定义以下接口：

- `AuthAdapter`：登录、刷新身份和退出；
- `LocalStoreAdapter`：草稿、幂等键和最近使用项；
- `FilePickerAdapter`：拍照、相册、文件和压缩；
- `UploadAdapter`：分片、重试、进度和取消；
- `QrCodeAdapter`：扫码和活动入口；
- `NotificationAdapter`：站内通知、微信订阅消息或 Web 通知；
- `NetworkAdapter`：在线状态、重试策略和同步触发；
- `DeviceInfoAdapter`：设备、版本和诊断信息。

业务功能只依赖这些统一接口，不直接依赖微信全局对象、浏览器专有 API 或未来原生 SDK。

## 6. 登录与身份

服务端身份模型必须独立于登录渠道。

首期可支持：

- PWA：手机号验证码、已有账号登录或一次性链接；
- 微信小程序：微信登录换取服务端会话，并按需要绑定手机号或既有账号；
- 临时参与者：受限的一次性链接、二维码令牌或活动临时身份。

同一个自然人可能通过不同客户端登录。账号绑定和合并必须保留审计，不能因为微信身份与手机号身份重复而产生两个无法识别的资金经手人。

## 7. 弱网与离线

两端都必须实现：

- 未提交表单自动保存；
- 提交请求携带客户端幂等键；
- 图片先进入本地上传队列；
- 网络恢复后可继续上传和提交；
- 明确显示草稿、上传中、待同步、已确认和失败状态；
- 重试不能产生重复资金流水；
- 冲突不能静默覆盖已确认记录。

PWA 和微信小程序的本地存储容量、后台执行和生命周期不同，因此离线能力通过统一语义、不同实现完成，不要求底层机制完全一致。

## 8. API 与版本兼容

- PWA 与微信小程序使用同一套业务 API；
- API 不根据客户端类型改变资金语义；
- 客户端需上报应用类型和版本，仅用于兼容、诊断和灰度；
- 服务端在废弃字段或行为前需要兼容窗口；
- 关键资金操作优先采用服务端领域命令，而不是客户端拼装多条流水；
- 内部转移、垫付和报销等复合动作必须由服务端原子完成。

## 9. 测试要求

每个资金功能至少验证：

- PWA 和微信小程序均能完成核心正常流程；
- 两端生成的 API 请求具有相同业务语义；
- 确认摘要一致；
- 金额、来源和目标校验一致；
- 重复点击与网络重试不重复记账；
- 不同客户端交替操作时余额一致；
- 权限和活动数据范围一致；
- 附件上传失败可以恢复；
- 老年或低熟练用户可完成高频操作。

共享业务场景应尽量采用契约测试驱动两个客户端，平台特有能力再增加端侧测试。

## 10. Android/iOS 启动条件

满足以下一种或多种情况后，再正式评估原生客户端：

- PWA 或微信小程序的离线能力无法满足真实活动；
- 需要稳定后台任务、推送、蓝牙、NFC、系统级文件或相机能力；
- 需要应用商店分发、设备管理或企业部署；
- 性能、可靠性或无障碍体验经优化后仍不达标；
- 海外用户难以使用微信小程序，PWA 又无法满足关键需求；
- 已有稳定 API、领域模型和跨端测试集，可降低原生端返工。

原生端应复用 API 契约、领域类型、场景测试和平台适配思想，不重新定义资金规则。

## 11. 非目标

首期不要求：

- PWA 与小程序像素级一致；
- 四个平台同时发布；
- 将全部页面一次性做成离线可用；
- 依赖微信平台保存正式业务事实；
- 在客户端计算或缓存唯一一份正式资金余额；
- 为追求代码复用而牺牲平台可用性。

## 12. 验收标准

- PWA 与微信小程序的首期范围明确；
- Android/iOS 被列为后续阶段且不阻塞 MVP；
- 核心业务规则和 API 契约可跨端复用；
- 平台能力通过适配层隔离；
- 两端均覆盖资金正确性、弱网、权限和附件场景；
- 平台差异有记录、测试和降级方案；
- 任何客户端均不能绕过服务端资金规则。
